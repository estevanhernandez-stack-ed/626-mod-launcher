### A1. Registered games never pick up corrected manifest facts · `M` · **DONE 2026-08-09**

**Problem.** `GameEntry.FileExtensions` (and its siblings) are written **once, at registration**
(`EnginePresets.cs:86` — `input.FileExtensions ?? preset.FileExtensions`) and frozen into
`games.json`. `EffectiveManifest` merges remote-over-embedded for the *manifest*, but nothing ever
re-applies a corrected definition to a game the user already added.

**Observed.** Este's Cyberpunk 2077 registered with `fileExtensions: ["pak"]` while the manifest
says `["archive"]`. `Scanner` builds `ctx.FileRe` from the registered value, so **194 `.archive`
mods on disk showed as zero mods in the launcher** — and the discovery sweep was blind for the same
reason (`DiscoverySweepOptions.EngineExtensions` is `ctx.Game.FileExtensions`). Repaired by hand on
2026-08-05 (backup at `games.json.bak-20260805-080157`).

**Why it matters beyond one game.** This silently voids the manifest feed's core promise — *"a new
game on a known engine needs no app release."* Every definition correction we mine only reaches
users who had NOT already added that game. The longer a user has had the launcher, the less the
feed helps them.

**Proposed fix.** At context-build time (in memory — never rewrite `games.json`), prefer the
manifest's value when the registered value still equals the **engine-preset default** and the
manifest carries a specific one. A user who genuinely customized a field keeps it; a user carrying
a stale preset snapshot gets the correction. Changes only what the scanner *looks for* — no file
op, so it stays inside the reversibility law.

**Open Q — resolved by measurement.** Preset-default equality was the proposed heuristic for
"untouched", with a `userSet` marker as the exact-but-needs-migration alternative. Checked against
every real registration on the dev machine, the heuristic separates them correctly:

| game | stored | preset default | verdict |
|---|---|---|---|
| cyberpunk-2077 | `["pak"]` | custom → `["pak"]` | matches → stale, corrected to `["archive"]` |
| marvel-s-spider-man-2 | `[".smpcmod", …]` | custom → `["pak"]` | differs → user's, kept |
| windrose | `["pak","ucas","utoc"]` | ue-pak → same | matches, manifest silent → kept |

So the marker (and its migration) buys nothing today. `RegistrationRefresh` in Core carries the rule
with tests; order and case do not count as customisation (they are not choices a user makes), but a
SUPERSET of the preset default does. Applied at context-build time only — `games.json` is never
rewritten, so what the user chose stays visible and editable. Verified end to end: the exact stale
Cyberpunk shape goes from 0 mods visible to 2, while a deliberately-chosen extension list is left
alone. Covers `GroupingRule` as well, which froze the same way.

### A4. An agent could not tell "managed" from "organized" · `M` · **DONE 2026-08-09**

Found by failing at it. Asked whether Elden Ring's mods had been reorganized, the agent ran a dozen
filesystem probes and reached a confidently WRONG answer twice — first "626 shows zero mods for Elden
Ring, for everyone", then a proposal to delete a Vortex staging folder as redundant. The launcher had
the correct answer on screen the whole time ("Detected 11 mods — loose-file install, no Mod Engine 2
needed"). The agent surface could not be asked.

Three things made the wrong answer easy to reach, all now fixed:

- `get_mod_context` reported the DECLARED mod location with no reality check. Elden Ring declares a
  Mod Engine 2 `mod` folder that does not exist; every mod loads by direct-inject under `Game\`.
  Declared-as-fact reads as a broken install. Now carries `exists` + `absolute` per location.
- `location` on a mod is the listing LANE (`direct-inject`), not a place — so nothing could say
  whether content sat in `Game\mods\` or loose in `Game\`. `files` and `isLoader` were on the
  record all along and simply never surfaced; both are now exposed.
- `mod` vs `mods` are different folders, and a truncated directory listing hid the second. Containment
  now tests on a separator boundary, with a test pinning that pair specifically.

`GameShape` (`src/ModManager.Core/Discovery/GameShape.cs`) puts declared and actual side by side:
mechanism, play folder, declared locations with `exists`, the real directories mods were found in,
loaders present, an alignment verdict, and plain-language notes. Exposed as `get_game_shape`.

**The design call worth keeping.** "Organized" was the obvious framing and it is wrong. A
direct-inject mod is DEFINED by living loose at the play-folder root — `dinput8.dll` is a loader,
`reshade-shaders` is read from the root by name. A tidiness verdict would push a user to "fix" a
working install by breaking it. So the report never judges tidiness; it reports ALIGNMENT — were the
mods found where the registration said to look — and states outright that drift is a description, not
a defect. Live results: Elden Ring `Drifted` (healthy, mechanism the registration never mentions),
Cyberpunk `Aligned`.

Read-only, like every discovery surface. `.mcp.json` now wires the server, which was built but
unreachable — `{"mcpServers": {}}`.

### A5. The discovery sweep and the mod-key formula can disagree after a manifest refresh · `S` · **DONE 2026-08-09**

Found by the whole-branch review of the registration-repair work, reading this branch against the
commit before it. Pre-existing on master since A1 landed (`2e0b36a`) — not introduced by that branch,
but made reachable by it.

`MainViewModel.cs:2700-2703` carries the comment *"ctx.Game.FileExtensions is the exact value
ctx.FileRe (and therefore Scanner.ModKeyFor) is built from — using anything else would let the sweep
and the key formula disagree."* That stopped being true when `RegistrationRefresh` landed: `ctx.FileRe`
is now built from `declaredExts`, which may be the MANIFEST's list rather than the stored one. Same
shape at `Scanner.cs:1408` and `Scanner.cs:1514`, which branch on `c.Game.FileExtensions.Count > 0`
rather than on `c.Exts`.

So for exactly the case A1 exists to fix — a stale `["pak"]` corrected to `["archive"]` — the sweep and
the key formula *do* disagree. Fix is to read `c.Exts` (the resolved value) at all three sites and
correct the comment. Cheap; needs a test that a refreshed registration produces the same keys through
both paths.

**Fixed 2026-08-09.** `GameContext` now carries `DeclaredExts` — the resolved-but-unnormalised list,
assigned from the same local `ctx.FileRe` is built from — and all three sites read it.

One of the three was **live**. `DiscoverySweepOptions.EngineExtensions` was the raw stored value, so on
a stale Cyberpunk registration the scanner listed all 194 `.archive` mods while `IsEngineShaped` refused
to call a single one of them engine-shaped: the launcher showed the mods and "Identify my mods" could
not see them. The other two — the `Count > 0` branches in `Md5IdentifyArchivesAsync` and
`ArchiveModKeysFor` that pick extension-based vs catalog-based keying — were **latent**. They ask only
whether the list is empty, and `cyberpunk-2077` is the only manifest entry carrying `fileExtensions`
today, on the `custom` preset whose default `["pak"]` is already non-empty. Stored and resolved agree on
emptiness for every registration that exists right now. They diverge the moment the feed gives
extensions to a game whose preset default is empty (`smapi`, `fromsoft`, `decima`) — which needs no app
release, so it is a data change away.

**The proposed fix above was wrong and is left as written.** `c.Exts` was `DeclaredExts` *plus*
empty→`["pak"]` substitution, lowercasing, dot-trimming, and `Regex.Escape`. Using it would have made
the sweep fire on `.pak` for the three folder-based engines that genuinely have no extensions, and the
escaping broke a plain `Contains` for any extension holding a regex metacharacter. The three values are
easy to confuse, which is why `DeclaredExts` ships with a doc comment naming how it differs from both
neighbours. Four tests in `tests/ModManager.Tests/GameContextDeclaredExtsTests.cs`: the live bug, the
emptiness invariant the two Scanner branches rely on, a guard proving the two can diverge (injected via
`EffectiveManifest.SetRemote`), and the substitution difference. (A7 below has since moved the
`Regex.Escape` out of `Exts` and into the `FileRe` interpolation, so only the substitution now separates
the two lists — the reason the sweep must still read `DeclaredExts` is unchanged.)

### A7. Intake classified a regex-metacharacter extension as "skip" · `S` · **DONE 2026-08-09**

Found by the A5 review, reading `GameContext.Exts`'s own doc against its callers.

`ctx.Exts` was `Regex.Escape`d, and seven intake sites passed it to `Intake.ClassifyDrop`, which
compares by literal equality (`Intake.cs:15-23`). A game declaring `mod+pak` got
`Exts = ["mod\+pak"]`, so a real `foo.mod+pak` classified as **skip** — listed by the scanner (whose
regex escapes correctly), refused by intake. Reachable through every one of the seven: loose drop,
zip entry, dropped-folder walk, `ArchiveModKeysFor`, and readme capture. Confirmed by failing test,
not by reading.

**The prescription first filed with this entry was wrong, and so was the doc it came from.** Both
said the fix needed a third list or a `ClassifyDrop` flag, because *"those sites depend on the
empty→`["pak"]` substitution … empty is meaningful — it is how a folder-based engine is told apart
from an extension-based one."* The second half is true of the unsubstituted list; it is not why the
intake sites need the substitution. They need it because **an extension-less registration is a pak
game to every other reader**: `GameEntry.FileExtensions` defaults to empty, so any hand-written or
quick-added entry that omits the field gets `FileRe = \.(pak)$`, `ModKeyFor` stripping `.pak`, and
the scanner listing lane showing `.pak` files as mods. Moving intake alone onto the unsubstituted
list would have made intake the one reader that disagrees — a mod visible in the list that cannot
be added.

The folder-based engines the entry invoked neither want the substitution nor depend on it:
`fromsoft` never reaches these sites (the App routes it through `DirectInjectService`, and
`ArchiveModKeysFor` / `Md5IdentifyArchivesAsync` branch to `DirectInject.MatchSignaturesInZip`), and
`decima` early-returns to `LooseRootIntake.Plan`. So the substitution was worth keeping, for a
different reason than the one given.

**Fixed** by making the escaping local to the regex rather than adding a third list: `ctx.Exts` now
carries the extensions themselves (lowercased, dot-stripped, empty→`["pak"]`), and
`Scanner.GameContext` applies `Regex.Escape` at the point it interpolates them into `FileRe`.
Nothing else in the codebase read `Exts` — the escaped spelling had exactly one consumer group, and
that group compared it literally. `FileRe` is byte-identical for every input, pinned by test. Two
values in `GameContext`, not three.

Left open, separately: `smapi` games do fall through to `Scanner.PlanIntake` with the substituted
`["pak"]`, so dropping an archive that happens to contain a stray `.pak` copies it flat into `Mods/`
where SMAPI cannot load it. That is not the escaping bug — SMAPI intake (folder-shaped mods carrying
a `manifest.json`) is simply not implemented, and narrowing the substitution would not implement it.

### A9. SMAPI intake places a stray `.pak` flat in `Mods/` · `S`

Found while verifying A7's premise, and deliberately not folded into that fix.

`smapi` has no `loose-root` form and is not direct-inject-backed, so it reaches `Scanner.PlanIntake`
with the empty→`["pak"]` substitution applied — meaning a `.pak` inside a dropped archive classifies
as a mod for a Stardew game and lands flat in `Mods/`. A SMAPI mod is a FOLDER containing a
`manifest.json`, never a loose pak.

This is not a list change. Fixing it by taking the substitution away from intake would make intake
refuse a mod the scanner listing lane already shows (see A7's verdict — an extension-less registration
is a pak game to `FileRe` and `ModKey`). It needs folder-shaped SMAPI intake: recognise the
`manifest.json` marker and place the containing folder, the way the framework installers already do.

### A10. The updates list renders a version pair it cannot fill · `S` · Este, 2026-08-17

Found while shooting Store screenshots — the second time now that the shop window has surfaced a
defect nobody had filed. Shot 4 of the listing set is the updates view, and roughly twenty
consecutive rows read **`unknown -> 1.2.1`**. Others read **`1.1 -> 1`**, **`1.0.1 -> 1.0.0`** and
**`1 -> 1.0`** — two apparent downgrades and a no-op, all presented as updates. Header said
*115 updates*.

**Do not "fix" `Mod.UpdateAvailable`.** That precedence is deliberate and the reasoning is written
out at `src/ModManager.Core/Mod.cs:62-87`: an unknown installed version already refuses to claim an
update, and the clause exists because a 98-mod live smoke lit the UPDATE chip on every identified row
at once. The comment's own warning is the thing to keep in mind here — *"a false positive shaped like
the truth never gets reported."*

The actual shape: `NexusUpdateAvailable ?? (version compare)`. Nexus's per-user flag **outranks** the
compare, and rightly so — Nexus knows which file the user downloaded and we often do not. So a row
can be listed entirely on Nexus's authority while we hold no installed version at all. The listing
then renders `installed -> latest` regardless, and prints `unknown` on the left.

So this is presentational, not a correctness bug in the decision:

- When the listing reason is the Nexus flag rather than a version difference, say that
  (*"Nexus says you're behind"*) instead of printing a comparison we cannot stand behind.
- Never render a pair that reads as a downgrade or a no-op. `1.1 -> 1` and `1.0.1 -> 1.0.0` are worse
  than showing nothing — they invite the user to "update" backwards.
- Reconsider what the count means. *115 updates* is counting rows we cannot substantiate, and the
  badge is load-bearing on the library home.

Where: `src/ModManager.Core/ModUpdateSummary.cs` mirrors the same three inputs and drives both the
badge and this view; the row rendering is the updates view in the App layer.

### A11. One multi-option mod becomes several identical update rows · `M` · Este, 2026-08-17

Same screenshot. **"Faster Ships" appears four times** in the 0.17 capture and three times in the
0.18 one, every row identical, every row `1 -> 1.0`.

Root cause is already understood and was recorded in an earlier session: Nexus tracks downloads
**per file**, not per mod, and a multi-option mod publishes several. Faster Ships ships
`FasterShips10`, `FasterShips10_B`, `aaUltraFastShips`, `aaUltraFastShipsB` — those variant chips are
visible on the mod's own row in `docs/store-assets/screenshots-0.17/06-settings.png`. Each tracked
file produces its own update row.

The launcher already understands variant families elsewhere (the chips exist, and C6 taught the name
matcher to refuse a wrong-attach across a variant family). The updates view is where that knowledge
has not landed: group by mod id, show the mod once, and put the file options underneath if they are
worth showing at all.

Related to A10 only by symptom — A10 is what a row says, this is how many rows there are. They will
read as one bug to a user and should probably be fixed together, but they are separate causes.

### A12. The mod count disagrees with itself across three surfaces · `S` · found by the harness, 2026-08-17

The first real smoke-harness run caught this, which is the point of building it. For Windrose:

| Surface | Count |
|---|---|
| Library home row | **30** mods |
| MCP `get_game_shape.modCount` / `list_mods` | **30** |
| Game view (rows + `AppStatusText`) | **27 of 27 enabled** |

The gap is exactly the Faster Ships family. `list_mods` returns `FasterShips10`, `FasterShips10_B`,
`aaUltraFastShips` and `aaUltraFastShipsB` as four entries, all with `displayTitle: "Faster Ships"`;
the game view groups them into one variant row. 30 - 3 = 27. Neither number is wrong on its own
terms - one counts mod keys, the other counts rows a human sees.

**It is a parity violation, though, and against the rule this repo wrote down a day earlier.** Under
*parity, plus the reason* (section E), an agent must see what a human sees. An agent reading the MCP
today confidently reports "you have 30 mods"; the user opens the game, counts 27, and concludes the
agent is wrong. The MCP should expose both - the row count a human would count AND the key count -
with the grouping named, rather than one number that silently means something different from the
screen.

The home row has the same problem without the excuse: it is a human-facing surface showing 30 next to
a game whose own view shows 27.

Related to **A11** and probably one fix: both are the variant-family question, asked once about
update rows and once about counts. Worth doing together.

Also spotted in the same `list_mods` output: **`shared` is listed as a mod** - `"displayTitle":
"Shared (UE4SS internal)"`. That is UE4SS's own internal folder, not a user mod, and it is inflating
every count above. Cheap to exclude; verify against `isLoader` handling first, since something
deliberately named it rather than hiding it.

### A13. Framework detection ORs together two files that are actually AND · `M` · proven live, 2026-08-17

**626 reports a healthy install while the game itself refuses to start its mods.** Proven end to end
on Este's Windrose, not reasoned about.

`FrameworkDeps` documents `DetectRelativePaths` as *"if ANY exists under the resolved candidate roots,
the framework is considered present. Multiple paths cover loader variants."* For UE4SS the two paths
are:

```
Binaries/Win64/ue4ss/UE4SS.dll     <- the runtime
Binaries/Win64/dwmapi.dll          <- the proxy loader that loads it
```

**Those are not variants. They are a chain.** The game loads `dwmapi.dll`, which loads `UE4SS.dll`.
Both are required. OR semantics mean either one alone reads as "framework present".

**The experiment.** Moved `UE4SS.dll` aside, left `dwmapi.dll` in place:

| | |
|---|---|
| 626 status line | `27 of 27 enabled` |
| `NEEDS UE4SS` chips | **0** |
| The game, on launch | **"Failed to load UE4SS.dll"** — its own error dialog |
| `UE4SS.log` | never written. Still Aug 2, still 1074 lines |

Twelve ue4ss-lane mods were dead and the launcher said everything was fine.

**This is the dangerous direction.** A false RED chip is noise; a false GREEN is a user who thinks
their mods are on. Este remembered the opposite symptom — red chip, mods working — which is worth
recording because the real failure is the one nobody notices.

**Same shape elsewhere, unverified but suspicious:** BepInEx lists `BepInEx/core/BepInEx.dll` and
`winhttp.dll` — runtime and proxy, same AND-as-OR. Check every entry before fixing; some lists are
genuinely alternatives and must stay OR. Elden Mod Loader's `dinput8.dll` / `version.dll` /
`winhttp.dll` / `SeamlessCoop/ersc.dll` ARE real proxy-name variants — OR is correct there.

**Shape of the fix:** the record needs to distinguish *any-of* (loader name variants) from *all-of*
(loader plus runtime). Probably two lists rather than one, so the same type expresses both without
the caller guessing which it got.

**Also worth its own look:** the `Refresh` in 626 did not notice either. The check runs on scan and
the file vanished underneath it — defensible, but "Steam updated this game, recheck your mods" is
already a banner this app knows how to show, and a missing framework deserves the same treatment.

### A6. Follow-ups the registration-repair reviews found and deliberately deferred · `S`

Raised during the per-task and whole-branch review passes on `feat/registration-repair-ui`. None
blocked the merge; each was consciously deferred with a reason.

- `DataDirMove.Plan` walks the whole data directory on every `RegistrationChange.Plan` call, so the
  setup dialog re-walks it on every pause in typing (a 250ms debounce mitigates but does not fix it).
  Fix: memoize `DataDirMove.Plan` in Core, keyed on the normalised `(from, to)` pair —
  `DataDirMove.Norm` already exists for this.
- `RegistrationChange.SameLocations` compares list COUNT first, so any caller that reshapes the
  location list reads as a user edit and false-pins `modLocations`. That was patched twice at the
  call site during this work (the `>1` and `==0` cases). **The obvious test is not the fix.**
  `Plan(stored: [], proposed: [])` already passes against today's implementation, so writing it buys
  a regression guard and nothing more — and it does not touch the actual hazard, which is a CALLER
  reshaping the list (`1 → 3`, `0 → 1`) and the planner reading that reshape as a stated choice. A
  test that proves anything has to assert on a reshape, or A6 gets closed with a green test that
  proves nothing.
- **Two decisions still in the App that belong in Core**, both currently unreachable by a test:
  1. The pin target. `RegistrationRepairService.SaveAsync` writes `Scanner.DataDirForGame(stored)` —
     STORED, not proposed, because the point of a pin is to name where the data already is. Getting
     that one word wrong writes a `dataDir` pointing at a folder with nothing in it. The rule deserves
     to sit next to `DataDirMove` behind a test.
  2. The orphan message. The double-failure and source-survived branches are the highest-stakes
     strings in the feature and are asserted by nobody. `DataDirMove.SpaceRefusal` is already
     `internal` precisely so a test can hold a user-facing string to account; the same precedent
     applies here.
- **A breadcrumb at `move.To`.** The move runs before the registry write, so process death in the
  window between them leaves the data at the new path and the registration at the old, with no record
  that a move happened. A small marker file written into the target before the move and removed after
  the successful write would make that recoverable on next launch instead of silent. (The read-back
  added for the concurrent-write case covers the writer-clobber half; it cannot cover process death.)
- **Only the first mod location is editable.** The setup dialog edits `ModLocations[0]` and carries
  the rest through untouched. A user whose SECOND location is wrong has no repair path here at all —
  they are back to hand-editing `games.json`, which is the situation this feature exists to end.
- **`games.json` has no lock.** `LoadRegistry → change → SaveRegistry` is shared, unlocked, and
  app-wide (`StampLaunch`, `SetActiveGame`, `Redetect`, discovery, and now the repair save). The
  repair save reads its write back and reports a clobber rather than going silent, which is the cheap
  half. Real serialisation — a single writer, or a file lock — is the proper fix.

### A3. `.archive.xl` sidecars are invisible and get orphaned on toggle · `S` · **DONE 2026-08-05** (`45edf7e`)

Cyberpunk's ArchiveXL mods ship `Foo.archive` **plus** `Foo.archive.xl` (91 of them in Este's
install). `DiscoverySweep.Extension` and `ctx.FileRe` both read only the final segment, so `.xl`
never matches `archive` and the sidecar is not part of the mod. Toggling the mod off moves the
`.archive` to holding and **leaves the `.xl` behind**, pointing at a file that is no longer there.

**Fix shape.** Treat a compound sidecar as belonging to its base mod key so it moves with it.
Needs care: the sidecar must not become its own row, and the grouping has to survive
`Scanner.ModKeyFor`. Verify what ArchiveXL actually does with an orphaned `.xl` before sizing.

### D3. The avatar picker opens on an empty box instead of the app's own icon · `XS` · Este, 2026-08-17

Settings → Identity offers "Pick an image — a Discord avatar, a screenshot, a photo. Use it as the
launcher's icon and derive a theme from its colors." Next to that copy is an **empty grey square**
until the user picks something. See `docs/store-assets/screenshots-0.17/06-settings.png` — it is
blank in the shipped listing shot, which is how long it has looked like that.

**Seed it with the app's own icon.** The control is asking the user to replace something, and it
currently shows nothing to replace. An empty box makes the user guess what the field does and what
size or shape is wanted; the 626 mark sitting there answers both without a word of copy, and it
demonstrates the outcome — *this is the thing that will change* — rather than describing it.

It also makes the derived-theme checkbox underneath legible. "Save a theme derived from these colors"
is abstract next to a blank square and obvious next to an actual image.

Small print worth getting right, because the difference is the whole point:

- The seeded icon is a **placeholder, not a selection.** Opening Settings and pressing Apply must not
  write the app icon as if the user had chosen it, and "Remove avatar" should return to the seeded

### C1. One long-operation slot, guarded per-method · `S` · **DONE 2026-08-06**

### C6. Name matching attaches the WRONG mod on a variant-family filename · `M` · **DONE 2026-08-09**

Confirmed against the Nexus files list for "Apartment Cats - Custom Cats": all six
`#ApartmentCatsCustoms_*.archive` files on disk ship from that ONE mod page. The sibling mods
("Apartment Cats - Dogtown", "- Corpo Plaza", "- The Glen", ...) are separate mods the user does not
have. Measured on the shipped matcher, with the true owner present in the candidate set:

| filename | picks | |
|---|---|---|
| `_Base` | (none) | miss |
| `_Dogtown_Black` | Apartment Cats - **Dogtown** | **wrong mod** |
| `_Corpo_BlackAndWhite` | Apartment Cats - **Corpo Plaza** | **wrong mod** |
| `_Glen_GreyTiger` | Apartment Cats - **The Glen** | **wrong mod** |

Not "fails to match" — attaches a different mod's identity, above threshold, pre-checked in the
review dialog. A wrong metadata attach is the thing this repo most fears, and it is reachable today.

**Two of the three come from the title-coverage fallback** (`3f45b60`): those queries score 0.38 and
0.43 Jaccard and are accepted only by coverage. The third (`_Dogtown_Black`) clears plain Jaccard at
0.60. The query ladder (`53f2eb9`) is what supplies the sibling candidates in the first place — it is
correct about retrieval, but it widened the pool an asymmetric acceptance rule draws from.

**Why every symmetric or set-based rule fails here.** The true owner and the wrong sibling are both
full subsets of the filename's tokens once plurals are folded, and both score identically. The only
signal that separates them is WORD ORDER, which Jaccard and coverage both discard:

    "Apartment Cats Customs Dogtown Black"  contains  "Apartment Cats Custom(s)"  contiguously
                                            does NOT contain  "Apartment Cats Dogtown"  contiguously

**Proposed rule:** a variant file is its parent's title PLUS a suffix. Prefer a candidate whose full
title appears as a contiguous run in the query, and refuse when two candidates are otherwise
indistinguishable. Verified by hand against the five good matches from the same live run
("Slaught-O-Matic Platinum Semi-Auto" → "Slaught-O-Matic Platinum" is a contiguous prefix) and both
bad ones — it keeps all five and rejects both.

**Shipped as the contiguous-run rule**, chosen by measuring five candidate rules against the real
corpus (six Apartment Cats files plus three known-good matches from the same live run) rather than by
reasoning. Two things the measurement caught that argument would not have:

- **A plural fold alone looked best and is a coin flip.** It scored 7/9 with the true owner and a
  wrong sibling TIED at 0.60 — it only "won" because the right answer happened to sit first in the
  candidate array. Reversing the candidates flipped it to the wrong mod. Every rule is now checked
  against reversed candidate order, and an order-dependent answer counts as a failure.
- **The last gap was an asymmetry, not the rule.** `CleanModName` filters short all-caps tokens out
  of the QUERY but nothing filtered them out of candidate TITLES, so "Slaught-O-Matic Platinum" could
  never align with a query already missing that "O". Both sides go through the same cleaning now.

Final: **10/10 correct, 0 wrong, 0 missed, 0 order-dependent**, including an adversarial case where
no candidate owns the file. The rule is checked BEFORE Jaccard (a spelled-out title is the strongest
evidence available), requires at least two words, and refuses on a tie — two titles spelled out
equally well is not evidence, and guessing there is the wrong-attach this repo fears most.


## E. Agent access - let an agent verify the smoke and drive the app

Este, 2026-08-17: *"I want both a desktop agent and an IDE/CLI agent to be able to fully verify our
smoke test and use the app (within reason)."*

The framing, the tool surface and the ten safety laws already exist, and they are good —
`docs/superpowers/specs/2026-05-26-agent-access-design-sketch.md`. Read it first; none of it needs
re-deciding. What follows is the gap between that sketch and what is actually built, three months on.

**What shipped:** `src/ModManager.Mcp/` — a stdio MCP server importing Core directly, wired in
`.mcp.json`. Six read tools: `list_games`, `get_active_game`, `list_mods`, `get_mod_context`,
`get_game_shape`, `get_server_info`. It reads the registry off disk and works whether the app is
running or not, exactly as designed.

**What did not:** everything that lets an agent *do* anything. Zero of the sketch's nine write tools,
zero of its three live-app tools, no consent surface, no audit log, and five of its nine planned read
tools (`list_themes`, `list_save_mods`, `list_profiles`, `get_app_settings`, `dry_run_intake`).

The read half answers *what is true*. Este is asking for the other two thirds: *change something*,
and *confirm the app showed it*.

### The principle: parity, plus the reason

Este, 2026-08-17: *"I want the MCP to allow agents to see exactly what a human can see. But some of
those things might matter more to an agent, like the version numbers and whatnot. So I think the
agent would end up seeing more."*

That is the design rule for every read tool, and it is sharper than "expose the data". Two clauses,
and the second is the one that gets skipped:

1. **Parity.** Anything rendered in the UI is readable by an agent. If a human can see a chip, a
   count, a status line, an empty state or a disabled control, so can the agent. A gap here means an
   agent confidently reporting on a screen it cannot actually read.
2. **Plus the reason.** Where the UI renders a *conclusion*, the agent also gets the inputs that
   produced it. Humans read a rendered string; agents diagnose. The agent should see the fields the
   view-model consumed, not just the sentence it printed.

**A10 is the worked example, and it argues for clause 2 better than any principle statement.** A
human looking at that row sees `unknown -> 1.2.1` and can only conclude the app is broken. An agent
under this rule sees that the row was listed because Nexus's per-user flag said so, that no installed
version was ever recorded because the match came from a name search, and that the version pair is
therefore not a comparison at all. Same row, and only one of those two readers can file a correct
bug. A10 sat unfiled for months in plain sight of everyone who opened that screen.

So the read surface is not a serialisation of the UI. It is the UI's inputs *and* its output, with
the link between them intact: what was shown, and what made it show that.

### E1. The write half of the agent surface · `L`

The sketch's own "concrete next step" says: read tools first, *"defer the write tools and the
live-app channel to a second PR after read works end-to-end."* Read works end-to-end. This is that
second PR, and it is the item that makes an agent able to **use** the app.

Take the sketch's catalog as written — `set_mod_enabled`, `apply_loadout`, `intake`, `register_game`,
`apply_theme`, `install_save_mod`, `uninstall_mod`, plus `dry_run_intake` from the read list because
plan-without-writing is how an agent should approach anything destructive. Its ten safety laws are
the acceptance criteria, not decoration. Three deserve restating because they are where this goes
wrong quietly:

- **Reversibility is inherited, not re-implemented.** Every write goes through the same Core paths
  the UI uses. An agent that reaches around them is a second source of truth and a second set of
  bugs.
- **"Within reason" has a hard floor at the ban-risk gate.** `BanRiskRules.ShouldGateEnable` requires
  an explicit human acknowledgement. An agent that can set that acknowledgement itself has deleted
  the law rather than honoured it. The gate must refuse an agent outright and surface a code the
  agent can report back to its human — the human acks in the app, not through the tool.
- **Audit before capability.** The `agent-log.jsonl` in law 8 should land in the *same* PR as the
  first write tool, not after. A write surface with no record of what it did is not something to hand
  someone else's game folder to.

Open question the sketch left and this PR must answer: consent UI shape (law 7). Recommend the
simplest thing that is honest — a first-connect dialog naming the agent, approval for the session,
revocable in Settings. Which lands it squarely in **D1**'s territory, so sequence accordingly.

#### Two audiences, one surface

Este, 2026-08-17: *"I want complete access to the app, especially for development and testing."*

The sketch was written for one audience, a stranger's agent on a stranger's machine, which is why its
framing is a passenger seat. That is right for the shipped product and too tight for the person who
wrote it, working on his own library.

Resolve it as **one tool surface, two consent postures**, never two code paths:

- **Shipped posture.** The sketch's laws as written. Per-session consent, confirm required on
  destructive ops, refusals with codes.
- **Development posture.** Opt in, off by default, never reachable in a Store build. Consent
  pre-granted so a test run is not twenty dialogs, and the confirm-required ops callable directly.

What must NOT differ between them is the audit log and the Core paths taken. A dev posture that
writes through a shortcut is testing something the user will never run, which is worse than not
testing at all.

**The one thing with no dev bypass: the ban-risk gate.** The distinction is the whole reason this
stays safe while still being testable. An agent must be able to *reach* the gate and confirm it
refuses, and must never be able to *satisfy* it. Verifying that the gate blocks is exactly the smoke
case worth automating. An agent that can tick the acknowledgement to get past it has turned the
launcher into the thing this project exists not to be. Same in both postures, permanently.

### E2. An agent has no way to see what the app is showing · `L`

This is the half the sketch never covered, and it is the one with the receipts.

Every one of the four bugs in v0.18.0/v0.18.1 was invisible to everything we own. From the 0.18.1
reviewer letter, written a day ago: *"All four are WinUI code-behind or view-model changes and are
not reachable from the headless test suite."* Specifically — a game was added correctly and the home
did not repaint; the retries that caused produced duplicate registrations; a fresh install hid the
discovery lane; the default theme was wrong. **The MCP could have confirmed the registry was correct
in all four cases and still not caught a single one**, because every one of them was a question about
what the window was showing.

**Feasibility settled 2026-08-17** by a spike against the installed Store build with a real 27-mod
library open: `docs/superpowers/research/2026-08-17-uia-feasibility-spike.md`. Read it before
planning this. Headline: UIA reads and drives the shipped binary out of process, 625 elements in
0.8s, 163 invokable controls, 31 toggles, and `AppStatusText` reads back *"27 of 27 enabled"*. No new
dependency — `UIAutomationClient` loads in stock PowerShell 7.

**Correcting this entry's first draft, which was wrong.** It said the groundwork was "better than
expected" because `AutomationProperties` appear across the XAML. That grep did not separate the two
kinds. The real counts: **92 `AutomationProperties.Name`** (accessibility labels, for screen readers)
and **zero `AutomationProperties.AutomationId`**. Only 8 app-authored ids reach the live tree at all,
via WinUI's partial promotion of `x:Name`, out of 720 `x:Name` attributes in the XAML.

So identification currently rests on **display text**. Every control the harness needs is reachable
today only as `Name='Enable all'`, `Name='+ Game'`, `Name='626 Labs'` — UI copy, in a repo whose
conventions treat microcopy as something to keep improving. Rename a button and a green suite goes
red for no behavioural reason; move one and it keeps passing. Searching for `Play` returns a `Text`
element rather than the button, so a naive harness asserts against a label and never touches the
control.

That makes E2 a bigger job than first written, and the extra work is an **`AutomationId` pass**, not
harness plumbing. Scope it to what the triaged smoke list actually touches rather than all 720
`x:Name`s — which is another reason E3 goes first.

What to build:

- A UIA-backed harness that can enumerate the visible tree, read text and visibility, and invoke
  controls — out of process, so it tests the shipped binary rather than a test host.
- An audit of `AutomationId` coverage. The properties present were added for accessibility, not for
  automation, so assume gaps exactly where the interesting state lives (the discovery lane, the
  status line, the theme picker's selection).
- A bridge so both consumers reach it: the IDE/CLI agent through MCP tools, and a desktop agent
  driving the live app.

Worth saying plainly: this is the difference between *"the registry says the game is added"* and
*"the user can see the game."* Only the second one is the smoke test.

Parity applies here at its strictest, and the awkward case is the one that matters. **Absence has to
be readable.** Three of the four bugs in 0.18 were about something not being on screen: a lane that
should have appeared, a list that did not repaint, a state that never changed. A harness that can
only assert on what exists will pass all three. It has to answer "is the discovery lane visible" with
a real no, rather than with a lookup that finds nothing and shrugs.

#### Screenshots are a verification channel, not a debugging aid

Este, 2026-08-17: *"I do think there are opportunities where an agent can verify something looks
right. Screenshots during an automated UI test give the agent a view. You have caught things in
screenshots without direction."*

This is the correction to an earlier draft of E3, which parked "does it look right" in a human-only
bucket. That was wrong, and the evidence against it was produced in the same session that wrote it:
**A10 and A11 were both found by reading a screenshot**, while checking whether a Store listing image
was flattering. Nobody asked for a bug hunt. Both defects had been on that screen for months, in
front of everyone who opened it.

So the harness has two channels, and they fail in opposite directions:

- **Assertions over the UIA tree.** Deterministic, cheap, diffable, CI-safe. Catches exactly what
  someone thought to assert, and nothing else.
- **A screenshot read back to an agent.** Open ended. Catches what nobody thought to assert, which is
  the entire category that gets shipped. This is how twenty rows reading `unknown` and one mod
  appearing four times get noticed, because neither is a failing assertion anywhere. Every case in
  the harness should capture, whether or not it asserts on the image.

Worth keeping both honest about their limits. A screenshot read is not deterministic and must never
be a CI gate on its own; its output is a *finding to triage*, the same status as a review comment. And
where a property can be measured, measure it: the navy-versus-Forge check in this session came down
to sampling mean RGB across the frame and comparing the blue-minus-red delta against the old set,
which is a stronger claim than any description of a colour. Assert the measurable, capture
everything, and let the agent read what it was not told to look for.

Groundwork already exists: `scripts/capture-store-screenshots.ps1` does DPI-aware, exactly-sized
window capture and knows the WinUI 3 trap that PrintWindow returns blank against GPU composition.
Reuse it rather than writing a second capture path.

### E3. The smoke checklist is not something an agent can execute · `M`

`docs/smoke-tests/pending.md` is around sixty sections and 262 checkbox lines accumulated from late
May to now, in prose, ordered by the PR that produced them, with `merged YYYY-MM-DD` placeholders
that were never filled.

**The work is mostly done; the file does not know it.** Este, 2026-08-17: *"I've done most of that
smoke list, I just haven't checked it off."* So the unchecked boxes are not a backlog of untested
behaviour, they are a record-keeping debt, and the two ways to misread the file point in opposite
directions. Read it as a to-do list and you re-test things that were fine months ago. Read it as
history and you ship believing something was covered when it was not. Neither an agent nor a person
in a hurry can currently tell which box is which.

Three jobs, in order:

1. **Triage with Este.** He is the only one who knows what was actually exercised. Walk it with him
   and mark each entry verified, still pending, or obsolete because the surface no longer exists.
   Cheap, and nothing after it is trustworthy without it.
2. **Convert what survives** into a machine-readable artifact: preconditions, action, observable
   expectation, current status, and the release it was last verified against.
3. **Mark what an agent cannot do, explicitly.** That bucket is smaller than it first looks. It is
   not "anything visual", because a captured screenshot read back to an agent covers most of that
   (see E2). What genuinely remains is the cases needing something outside the app: a real game
   launched and played, a real Nexus download against a live account, hardware behaviour. Those stay
   human-only and stay *named*.

That third job is load-bearing. Este's goal is *"to achieve most of that smoke list with an agent"*,
most rather than all, and the gap has to stay legible. A harness that runs the automatable 80%,
reports all green, and says nothing about the other 20% manufactures precisely the false confidence
this repo distrusts elsewhere. It is the cherry-picked denominator wearing a different hat. Every run
summary should read *"N verified, M require a human, here is M."*

Do this **before** E1 and E2 rather than after. It is the specification those two are built to
satisfy, and writing a harness against a target that has not been defined is how you get a harness
that tests what was easy to test.

### Sequencing

E3 -> E2 -> E1. Define what verification means, build the ability to observe, then grant the ability
to act - so that the first agent write lands in a world where its effect can be seen and recorded.
D1 (Settings) intersects at E1's consent surface and E2's verification of it; take D1's design pass
with E1's consent dialog in scope rather than redesigning Settings twice.
