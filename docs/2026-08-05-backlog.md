  scheduled; each item gets its own spec → plan → build when it comes up the queue.
- **Sizing:** `S` one sitting · `M` a focused build · `L` its own multi-day feature.

## A. Correctness — found by smoke, real today

### A1. Registered games never pick up corrected manifest facts · `M` · root-caused

**Problem.** `GameEntry.FileExtensions` (and its siblings) are written **once, at registration**
(`EnginePresets.cs:86` — `input.FileExtensions ?? preset.FileExtensions`) and frozen into
`games.json`. `EffectiveManifest` merges remote-over-embedded for the *manifest*, but nothing ever
re-applies a corrected definition to a game the user already added.

**Observed.** Este's Cyberpunk 2077 registered with `fileExtensions: ["pak"]` while the manifest
says `["archive"]`. `Scanner` builds `ctx.FileRe` from the registered value, so **194 `.archive`
mods on disk showed as zero mods in the launcher** — and the discovery sweep was blind for the same
reason (`DiscoverySweepOptions.EngineExtensions` is `ctx.Game.FileExtensions`). Repaired by hand on
2026-08-05 (backup at `games.json.bak-20260805-080157`).

**Why it matters beyond one game.** This silently voids the manifest feed's core promise — *"a new
game on a known engine needs no app release."* Every definition correction we mine only reaches
users who had NOT already added that game. The longer a user has had the launcher, the less the
feed helps them.

**Proposed fix.** At context-build time (in memory — never rewrite `games.json`), prefer the
manifest's value when the registered value still equals the **engine-preset default** and the
manifest carries a specific one. A user who genuinely customized a field keeps it; a user carrying
a stale preset snapshot gets the correction. Changes only what the scanner *looks for* — no file
op, so it stays inside the reversibility law.

**Open Q.** Preset-default equality is a heuristic for "untouched." A `userSet` marker on the entry
would be exact, but needs a migration for existing installs.

### A2. No in-app way to repair a game registration · `S`

There is no edit-game dialog — `AddGameDialog` is add-only. A user whose registration is wrong (A1)
has no route out except removing and re-adding the game, which risks their per-game state. Even
after A1 lands, an explicit "edit this game's definition" surface is the honest escape hatch.

### A3. `.archive.xl` sidecars are invisible and get orphaned on toggle · `S`

Cyberpunk's ArchiveXL mods ship `Foo.archive` **plus** `Foo.archive.xl` (91 of them in Este's
install). `DiscoverySweep.Extension` and `ctx.FileRe` both read only the final segment, so `.xl`
never matches `archive` and the sidecar is not part of the mod. Toggling the mod off moves the
`.archive` to holding and **leaves the `.xl` behind**, pointing at a file that is no longer there.

**Fix shape.** Treat a compound sidecar as belonging to its base mod key so it moves with it.
Needs care: the sidecar must not become its own row, and the grouping has to survive
`Scanner.ModKeyFor`. Verify what ArchiveXL actually does with an orphaned `.xl` before sizing.

## B. Features

### B1. Close to tray · `S` · Este, 2026-08-05

Closing the window exits the app. Offer **close-to-tray** as an option, which also buys a tray
surface worth having: quick per-game actions, launch targets, update-available state, and a real
Quit. Settings toggle, default off (closing should still mean closing until the user says
otherwise).

### B2. Discovery falls back to a live Nexus name search · `M`

Tier 2 matches against the per-game `ModNameIndex`, seeded from the top ~500 browsable mods. That
is already "the browsable Nexus catalog, not just what we installed" — but a 194-mod Cyberpunk
library is mostly outside any top-500. Unmatched candidates should fall back to a **live text
search**, the way `LooseIdentify.ProposeAsync` already does (self-timeouting search delegate,
budget-capped). Reuses machinery that exists; the cap and the daily-budget interaction are the
design work.

### B3. Adopt another manager's library · `L`

The old Nexus Mods App keeps a 214 GB store at `%LOCALAPPDATA%\NexusMods.App\DataModel` holding
mods that are **downloaded but not deployed**. Anything deployed is already in the game folder and
therefore already ours to see; the undeployed remainder is invisible and always will be to a
game-folder sweep. If we ever adopt from a foreign library, adopt them **disabled** — an undeployed
mod is off, and turning it on is the user's call, through the normal reversible path.

**Prerequisite.** md5-ing a 214 GB store is not a sweep. This needs the foreign manager's own index
read, not brute force.

### B4. One mod, many trees · `M`

A single Cyberpunk mod spans `archive/pc/mod` (the archive), `r6/scripts/<Mod>` (redscript),
`r6/config` (tweaks), `red4ext/plugins`, and `bin/x64/plugins`. Este's install has all of these.
A game's single `modPath` can only ever describe one, so the launcher sees at most a third of such
a mod and would toggle only that third — a real reversibility concern, not just a display gap.

Needs a manifest schema conversation (multiple named mod trees per game, and which are toggle-safe)
plus a Core listing change. Spec B territory.

## C. Follow-ups from the identify-consolidation branch

Raised by the per-task and final whole-branch reviews, adjudicated as ship-now/fix-later. Listed
worst-first. None blocked the merge; all were consciously deferred with a reason.

### C1. One long-operation slot, guarded per-method · `S`

`IdentifyMyModsAsync` now has a re-entrancy guard. `EnrichMetadataAsync` does not, and both claim the
same `_longOpCts` / `IsCancellable` / `IsBusy` slot. Because Advanced items are deliberately always
visible and never disabled (*guard, don't hide*), a user can start "Refresh details from Nexus" while
an identify run is in flight: Stop then cancels the wrong run, whichever finishes first clears the
busy state for both, and two writers reach `Scanner.WriteManyMeta` while a third reads `_allRows`.

Not a data-loss or reversibility break — both writers write correct data through the same per-key
path — but a lost Stop button and a stale ring. `master` already carried this hazard with *two*
unguarded owners, so the branch strictly reduces exposure rather than widening it.

**Fix:** promote `_identifyRunning` to a single `_longOpRunning` guarding every entry point that
claims the slot. Touches a second feature's control flow, so it earns its own test and smoke pass.

### C2. The re-entrancy flag is set outside its `try` · `S`

`_identifyRunning = true` runs before the `try` block, with five statements between — including two
`[ObservableProperty]` setters that raise `PropertyChanged` synchronously into x:Bind handlers. A
throw in that window latches the flag for the session and silently bricks the app's primary new
action until restart. Low probability, one-line fix: make it the first statement inside the `try`.

### C3. Pass 4 never name-searches the swept candidates · `M`

The spec says the name search covers *"both swept candidates and existing unidentified rows."* The
delivered run searches `LooseIdentify.Candidates(_allRows…)` only. On a fresh game with a cold name
index, mods found by the sweep but not yet in the list are proposed as "not identified", and naming
them takes a **second** run of the whole action. Working as built, short of the spec as written.

**Fix or document.** Shipping it silently is the one option that isn't acceptable — a user who runs
the flagship action once and gets unnamed rows has no way to know a second run would name them.

### C4. Smaller nits

- `CancelLongOperation` writes `"Stopping…"` before checking there is anything to stop, so a no-op
  cancel leaves a false status line.
- Two comments over-claim: one says the two review dialogs' wording "can't drift" while their md5
  detail lines already differ ("Exact match by file hash." vs "Matched exactly by file hash."); one
  says the catalog surfaces gate on connection plus domain when two of the four gate on connection
  plus plugin capability only.
- `IdentifyRunOutcome` carries nine `<param>` tags but has no primary constructor, so they are
  silently discarded — and `GenerateDocumentationFile` is unset, so nothing warns. The best prose on
  the branch never reaches IntelliSense.
- The app now carries three different remedy strings for "Nexus not connected". One consolidation
  pass would fix it.
- `DesignLawTests`' dead-XAML-string allowlist is keyed by element name globally rather than by
  (file, name), so any future dialog naming a TextBlock `Blurb` is silently exempt.
- `TreatWarningsAsErrors` is set project-wide but 36 `MVVMTK0045` warnings survive the App build —
  something is suppressing escalation, so the guarantee is not what it says on the tin.

### C5. The same mod can appear twice in the review dialog · `S` · product call

When a mod is matched by BOTH the downloads-archive md5 pass and the name search, the dialog shows
it as two pre-checked rows — one per section — and the button reads "Apply 2 changes" when one will
land. The write-time behavior is correct (the md5 write wins; the name guess is filtered by
`LooseIdentify.ExcludeKeys`) and the summary explains the skip, but the dialog over-promises.

Deduplicating at propose time is NOT the fix — the classifier deliberately does not filter archives
against known row keys, because that would cost the md5 tier its shot at an exact identification.
The honest fix is cross-referencing the two lists by best-guess key when building the dialog and
rendering one row that names both pieces of evidence.
