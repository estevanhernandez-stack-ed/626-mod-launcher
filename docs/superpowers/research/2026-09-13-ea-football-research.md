# EA football research: the evidence behind the grand plan

*2026-09-13. Companion to `docs/superpowers/plans/2026-09-13-ea-football-grand-plan.md`.*

Produced by a research workflow: seven independent read-only dimensions, then one adversarial skeptic per load-bearing claim. Save bytes were inspected **only on hash-verified copies** of the owner's College Football 27 saves; the originals were confirmed byte-identical before and after. No game was launched, no anti-cheat was touched, no account action was taken, and no third-party tool was downloaded or run.

**Redacted.** This repository is public. Values decoded from the owner's own saves that identify his career — character name, school, schedule, week, rating, save-slot id — are replaced with `<redacted>`. The structure they describe is kept. Public EA roster data is not redacted.

Every finding carries the label its researcher gave it. **VERIFIED** means a named source, a file read, or observed bytes. **INFERRED** means reasoned, from what is stated. **UNKNOWN** means nobody knows.


## The load-bearing claims and their verdicts

All five were put to an adversarial skeptic told to break them. All five were confirmed, several with corrections. The corrections are in the verdicts.


### C1 — CONFIRMED

**Claim.** The EA app cloud-syncs every College Football 27 save except UserSettings.dat: RTG-E, RTG-E-AUTOSAVE, RTG-AUG30-10h40m00pm-AUTOSAVE, PROFILE-COLLEGE and ROSTER-Official, 5 files in all. Before launch it takes a lock and compares the local files with the cloud copy; after the game exits it pushes the local files to EA's S3 storage. VERIFIED from EADesktop.log, EADesktopVerbose.log and cloudsync\16425899_16425899.lastsync. What the sync does when the files were changed outside the game (keep local, take cloud, or ask), and what it does while the EA app is offline, is UNKNOWN.

**Why it is load-bearing.** This decides whether an at-rest edit survives at all and whether edited files reach EA's servers. The User Agreement names 'modified files' as enforcement evidence. It changes the safety disclosure ('fully offline' can't be promised), the required process checks (EADesktop must be closed as well as the game), how much a local snapshot restore can be trusted, and it adds an owner-run sync-conflict test before any real write. No other dimension inspected this; architecture-fit marked it unknown.

**If wrong.** If the sync pulls the cloud copy over local changes, every transported character or roster silently disappears the next time the user plays online, and sub-projects 3 and 4 deliver nothing unless the user stays offline permanently. If it pushes without checks, modified saves land on EA's servers and ban exposure is higher than the plan assumes. If it doesn't sync at all (contradicting the logs), the disclosure and EA-app-closed gating are over-built but harmless.

**Skeptic's reasoning.** I checked the EA app's own logs and cloudsync state files myself, read-only. Every part of the claim held up.

1. The EA app syncs 5 files. Its local-state scan lists PROFILE-COLLEGE, ROSTER-Official, RTG-AUG30-10h40m00pm-AUTOSAVE, RTG-E and RTG-E-AUTOSAVE under cloudId 16425899_16425899. The remote state points at cloudsync-prod.s3.us-east-1.amazonaws.com/prod/####/16425899_16425899 with "Number of files [5]" and a total size of 41,611,631 bytes. That total matches the five save sizes in the live saves folder: 87,702 + 12,582,986 + 3 x 9,646,981.

2. UserSettings.dat is not synced. It appears 0 times across EADesktop.log, EADesktop.bak, EADesktopVerbose.log and EADesktopVerbose.bak.

3. Before launch, it locks and compares. Each launch hits cloudsync.juno.ea.com/lock/read, then logs "Computing RemoteState/LocalState", then "compareStates: LocalState and RemoteState are identical", then "released pregame lock".

4. After exit, it pushes. The logs show lock/write, then "Pushing post-game local state", "Pushing local files to remote", "Pushed manifest to remote successfully", "Deleting unused files from remote" (S3 DELETE returned 204), "released post game lock" and "Post game cloud sync completed successfully". Remote files are stored under keys shaped content/<size>-<32 hex>.

5. The timing matches the last session. The most recent push ended at 2026-09-13T22:35:37-38Z, which is 17:35:37 local (UTC-5). That is the LastWriteTime of 16425899_16425899.lastsync, and 4 seconds after PROFILE-COLLEGE was last written (17:35:33).

The UNKNOWN parts are also correct. The logs contain only two branches: "identical" and the post-game push. I found no conflict, pull, download or offline branch for CloudSync. The logs cannot tell us what happens when files change outside the game, or what happens while the EA app is offline.

Two notes that do not change the verdict:
- The sync belongs to the EA app's launch and exit handling (it is logged by ProcessCoordinator). The logs do not show whether it also runs with no game launch.
- In the logs, "Pushing post-game local state" is chosen after comparing local state with remote state. So an edit made at rest, followed by a launch and exit, will probably be uploaded, unless the pregame compare pulls the cloud copy first. That is the conflict case, and it is still UNKNOWN.

**What would settle what remains.** The open question is what the sync does with a changed save. To settle it, the owner runs a test on a throwaway EA account or with a disposable save, while watching EADesktopVerbose.log for the CloudSync compareStates line:
1. Change one synced file outside the game while the EA app is closed. Launch online and note which branch appears: push local, pull remote, or a prompt.
2. Separately, repeat the launch with the EA app in offline mode and note the result.

The claim itself needs nothing more.


### C2 — CONFIRMED

**Claim.** College Football 27 FBCHUNKS saves have no app-level integrity check. Road to Glory, dynasty and profile saves carry only zlib's own Adler-32; writing means re-deflating, patching the compressed length at 0x4A, and keeping the exact fixed file size and header. VERIFIED: RTG-E and RTG-AUG30 differ in exactly 2 timestamp bytes, a table-header diff found no hash field, and the public madden-franchise save code computes no checksum. The roster's u32 at 0x1A is CRC-32/BZIP2 over the uncompressed data, VERIFIED on one unmodified official roster. Whether the game ACCEPTS a re-packed or edited save, or a roster with a recomputed CRC, is INFERRED/UNTESTED. FMT authors report edited rosters being rejected, and DaiyronW reports a save 175,232 bytes short hanging on load.

**Why it is load-bearing.** This is the core write-feasibility claim for sub-projects 3 and 4. It sets the writer design: libdeflate-class compression, a hard capacity and exact-size gate, keeping the tail region, and a CRC recompute for rosters. It also puts the owner-run acceptance test on the critical path before any translator work. The two reports disagreed on the roster field (one UNKNOWN, one matched as CRC-32/BZIP2), so it needs reconciling.

**If wrong.** If a hidden integrity check exists, such as a second hash at roster offset 26/28 as FMT claims, or server/Javelin validation of save structure, then every writer fails or bricks saves. Transport collapses to read-only export/inspection, or needs reverse-engineering far beyond the plan. A roster-only rejection would kill sub-project 4's roster-file path while character transport through RTG/franchise saves could survive.

**Skeptic's reasoning.** Every part of C2 marked VERIFIED held up when I checked it again myself on the copies. The part it marks INFERRED/UNTESTED is correctly labelled. I found nothing that points to a hidden integrity check. The headline "no app-level integrity check" is still an inference, though a strong one, and the claim needs four corrections before anyone builds a writer from it.

What I confirmed:
(a) RTG-E and RTG-AUG30 differ in exactly 2 bytes, at 0x1E and 0x20. Those are the minute and second of the u16 timestamp at 0x16 (2026-09-01 08:32:10 vs 08:31:55).
(b) In all three RTG saves the zlib stream starts at 0x52, and the u32 at 0x4A equals the exact compressed length (6,798,409 and 6,834,733). The Adler-32 trailer checks out.
(c) Every RTG header field is accounted for: 0x0A = header length 0x40, 0x0E = 0x933333, 0x12 = 0x933373 (0x40 + 0x933333), the timestamp, the build-name string, 0x3E = 0x341 (the same value appears in the FrTk table header at 0x2C), 0x4A = compressed length, 0x4E = 0. No slot is left over for a hash. The whole file was scanned for an existing CRC32 or Adler of the payload, and for its length.
(d) Roster u32 at 0x1A = 0x0D5B58BC. That exactly equals CRC-32/BZIP2 (poly 0x04C11DB7, init and xorout 0xFFFFFFFF, unreflected) over the 14,258,628-byte decompressed payload. It does not match standard CRC32, MPEG-2, or BZIP2 over the compressed bytes.
(e) madden-franchise FranchiseFileStrategy.postPackFile computes no checksum. It keeps the original 0x52-byte header, writes the new deflate length at 0x4A..0x4C, appends the new stream, then copies the original trailer from offset newLen+0x52, which keeps the file size fixed. No CRC, hash, MD5 or SHA code exists anywhere in the mf copy. Its README claims full College Football 27 dynasty support.

How the two reports reconcile: offset 26 is 0x1A, the CRC field itself. The local FMT README only says header "offsets/checksums need to be updated on write." It never names a second hash, and FMT's edited-roster rejections fit a writer that never recomputed this CRC. So the second hash is INFERRED to be the same field, not a new one. I could not find the specific "26/28 second hash" wording in the local FMT copies.

Corrections the writer design needs:
1. The layout is not uniform. PROFILE-COLLEGE has its zlib stream at 0x46, the decompressed length at 0x3E, and no compressed-length field (0x3E and 0x42 are 0x3D7F and 0x507EB). The roster has its zlib stream at 0x4A, the decompressed length at 0x12, the CRC at 0x1A, and also no compressed-length field. "Patch 0x4A" applies to RTG and dynasty only. Profile and roster writers must patch the decompressed length instead, if it changes.
2. The RTG tail is not padding. RTG-E has 2,848,490 tail bytes, 524,482 of them non-zero (RTG-E-AUTOSAVE: 544,939). It has structure: runs separated by zeros, each starting with a u16 length and then zstd frame magic 28 B5 2F FD (for example at 0x67BE4A, length 0x64). Some fragments also occur inside the decompressed payload. What it is, and whether the game reads it, is UNKNOWN. Profile and roster tails are all zeros.
3. The two public writers handle that tail in incompatible ways. madden-franchise keeps tail bytes at their absolute offsets, overwriting the front. DaiyronW shifts the tail and pads or trims only trailing zeros. Both are reported to work apart from DaiyronW's size-drift hang. That hints the tail is not validated by position (INFERRED, not tested).
4. The 2-byte diff only proves no hash covers the header timestamp. The two files have identical payloads, so a hash inside the payload would not show up in that diff. The actual evidence against a payload hash is (c) and (e), plus madden-franchise editing tables in place with no hash update. Game acceptance of any re-packed save is still UNTESTED by us.

**What would settle what remains.** Owner-run acceptance test, offline, game closed while files are placed, on disposable copies:
(1) RTG: decompress RTG-E-AUTOSAVE, re-deflate the unchanged payload at a different level so the bytes differ, patch 0x4A, keep the file at exactly 9,646,981 bytes with the tail at its original absolute offsets, then see whether it loads.
(2) Same, but also flip one known-safe field (for example a single attribute).
(3) Roster: re-deflate the unchanged payload, recompute CRC-32/BZIP2 into 0x1A, keep 12,582,986 bytes. Load it once with the correct CRC and once with the CRC off by one bit. If the bad-CRC roster is rejected and the good one loads, that proves the CRC is the check and that there is no second hash.
(4) Optionally, for RTG, also test DaiyronW's tail-shifting layout, to learn whether the non-zero tail matters.


### C3 — CONFIRMED

**Claim.** College Football 27 and Madden 27 share one franchise-file engine and nearly one Player schema: 255 common fields, including every *Rating, plus identical Position, PlayerType and TraitDevelopment enums. The trap is that TraitDevelopment aliases College_Impact/Star/Elite to Star/Superstar/XFactor as the same integers 1/2/3. This is VERIFIED only against the public schemas C27_468_2 and M27_620_0. The owner's RTG saves declare schema major 833 (VERIFIED at 0x3E), no public 833 schema is known, and the College schema drifted 468 to 809 to 833 across patches.

**Why it is load-bearing.** The whole plan to translate in Core between two dialects of one data model rests on this diff being valid for the owner's build. It drives the architecture (one league-neutral model with per-game field maps), the effort estimate, and the need for a per-build schema source: generating from table headers or extracting read-only from CAS files. It also requires build-tag and schema allowlisting that fails closed.

**If wrong.** If schema 833 renamed, re-typed or re-ordered Player fields, the field map writes plausible-looking garbage into saves that load but misbehave. Translation reverts to a full per-build reverse-engineering effort for both games, with a schema-extraction pipeline as a hard prerequisite, and every title update can silently invalidate the translator.

**Skeptic's reasoning.** I reproduced the claim from the schema files myself, then went further than the claim did. I tested the College 468 schema against the owner's own schema-833 Road to Glory saves. It held there for the College side.

(1) Public-schema diff: re-derived, with three corrections to the wording.
- VERIFIED: C27_468_2 Player has 288 members and M27_620_0 Player has 389. 255 names are common.
- VERIFIED: PositionE (6 bits), PlayerType (7 bits) and TraitDevelopment (3 bits) enum member lists are byte-identical across both schemas.
- VERIFIED: the trap is real. College_Impact, Star = 1; College_Star, Superstar = 2; College_Elite, XFactor = 3.
- Correction 1, "every *Rating" is not literally true. ProspectStarRating exists only in College. 56 Original*Rating fields plus PersonalityRating exist only in Madden. The core gameplay ratings are common.
- Correction 2, "identical" fields are not all identical. 8 of the 255 common fields differ in type or range:
  - ConfidenceRating: 0-127 vs 0-99
  - TeamIndex: 0-255 vs 0-32
  - PrevTeamIndex: 0-255 vs 0-32
  - PLYR_PREVTEAMID: 11 bits vs 10 bits
  - SkillPoints: 0-16384 vs 0-1000000
  - GenericHeadAssetName: maxLength 33 vs 26
  - PLYR_HOME_STATE: StateName vs PlaceName
  - Role: FranchiseRole vs BTCareerPersonaRole

  So a translator must clamp or re-map values. It cannot copy them straight across.
- Correction 3: TeamIndex semantics also plainly differ between the leagues (0-255 vs 0-32).

(2) The owner's build, the load-bearing risk.
- VERIFIED: RTG-E has u32le 833 at 0x3E, and 0x341 (833) also sits in the decompressed header.
- VERIFIED: the save's own Player table header (parsed with the public M20 header layout) declares numMembers = 288. That is exactly the 468 member count, not Madden's 389. Record size is 48 words (1536 bits), and all three RTG saves agree.
- VERIFIED: I paired the save's 288 per-member bit offsets with the 468 attributes in schema order. The offset gaps equal the widths the schema implies for 276 of 283 checkable fields. A random-permutation baseline gets 46-69. The 7 misses are all expected: computed int() fields, NearestCity, and end-of-record padding on PT_THROWAWAY.
- VERIFIED: I then decoded 3315 Player records using madden-franchise's own readOffsetTable 32-bit chunk algorithm from public source (FranchiseFileTable.js), under 468 names. Every value is plausible:
  - OverallRating 43-94
  - Height 66-81 inches
  - Age mostly 17-26
  - Position 0-20, the QB..P range
  - JerseyNum 0-99
  - SchoolYear 0-3
  - TraitDevelopment 0-3, distributed 2350 / 730 / 195 / 40, which looks like a Normal-heavy college roster
- So the College Player layout (order, widths, core field meanings) survived 468 to 833.

What is still UNKNOWN:
- Renames or re-meanings of same-width fields cannot be seen from offsets alone.
- Enum label-to-integer meaning in 833 is range-consistent only, not proven.
- The Madden side is entirely unverified for the owner's current Madden build. No Madden save exists yet, and it is not known whether 620 matches the live Madden schema.

Architecturally: the per-game field-map approach is supported, and schema-by-header validation is feasible. The save's table header carries numMembers plus a per-field offset table, so a fail-closed allowlist can check layout fingerprints per build without a public schema.

**What would settle what remains.** For the remaining Madden-side uncertainty:
1. Have the owner create one offline Madden 27 franchise save.
2. Copy it into scratchpad.
3. Read the schema major at 0x3E and the Player table header's numMembers and per-field offset table.
4. Run the same width==gap and plausible-value decode against M27_620_0.

For same-width renames on the College side, cross-check a few named values against known in-game facts. Examples: a known player's jersey number and position, or the owner's RTG character's Overall and dev trait as shown in the game UI.


### C4 — CONFIRMED

**Claim.** BanRiskCatalog resolves ban risk only by Stores.SteamAppId, and ByAppId(null) returns GameBanRisk.None. The embedded manifest carries no banRisk data, so risk exists only in the remote feed. ShouldGateEnable is called only from mod-enable paths, and the existing FromSoft save editor has no ban-risk gate. VERIFIED in BanRiskCatalog.cs, games-manifest.json, MainViewModel.cs, SaveEditorService.cs and WriteTools.cs. Registering the EA install WITH its Steam id instead makes EnginePresets set LaunchUrl=steam://rungameid/, launching through the wrong store. Madden 27 has no curated banRisk (mined row is null).

**Why it is load-bearing.** This sets sequencing: sub-project 1 (registering EA-app installs) cannot ship before risk resolution is keyed by manifest id or an EA id, has a compiled-in fail-closed floor for these Javelin titles, and has a Madden override curated. Sub-projects 3 and 4 need a new save-write gate (for example SaveTransportRules) with an acknowledgement an agent cannot give. Otherwise the launcher breaks its own warn-and-acknowledge law on a kernel-anti-cheat title.

**If wrong.** If some other path already resolves risk for games with no Steam id, or gates save writes, this prerequisite work is unnecessary and sub-project 1 can go first. If the claim holds and is ignored, CFB27 and Madden ship with no warning, no gate and no agent refusal, which is the most serious operating-law failure possible for this program.

**Skeptic's reasoning.** I tried to break each part of the claim by reading the source and data again, and every part held.

1. BanRiskCatalog.Build() (src/ModManager.Core/BanRiskCatalog.cs, lines 34-44) only adds a map entry when `g.Stores.SteamAppId is { } appId`. ByAppId (line 47-48) returns GameBanRisk.None for a null or empty id. It resolves by nothing else: no manifest id, no EA id, no persisted GameEntry field.

2. A grep of src for BanRisk found no second route. Every place that uses ban risk goes through BanRiskCatalog.ByAppId(game.SteamAppId):
   - LibraryViewModel.BanRiskFor, line 465
   - MainViewModel, lines 406, 486 and 1309 (warning visibility, the state-strip chip, and the enable gate)
   - WriteTools.SetModEnabled, line 64 (the MCP agent path)

3. ShouldGateEnable has two callers: MainViewModel line 1311 (the enable gate) and AgentWriteRules line 61, which only CanEnable reaches from WriteTools when enabled=true. Both are mod-enable paths.

4. SaveEditorService.cs, SavesDialog.xaml.cs, CharacterEditDialog and src/ModManager.Core/SaveEditor contain no reference to BanRisk, ack or a gate. SaveEditorService only snapshots with SaveManager.Backup. No MCP tool writes saves.

5. The embedded src/ModManager.Core/Manifest/games-manifest.json has 0 occurrences of "banRisk" and no College Football or Madden entry. The field only reaches runtime through EffectiveManifest's merge of the remote feed (EffectiveManifest.cs line 109, MaxString(embedded, remote)).

6. EnginePresets.BuildGameEntry (lines 90-94) sets `LaunchUrl = "steam://rungameid/" + SteamAppId` whenever a Steam id is given, with no store override. So this is a real bind: an EA-app install with the Steam id launches through Steam, and without the id its risk is None.

7. Feed repo 626-game-manifest/games-manifest.json: the ea-sports-college-football-27 row has steamAppId 4032350, banRisk "high" and safeRoute "offline" (curated override in overrides/ea-sports-college-football-27.json). The feed repo has no Madden entry at all. The miner draft (tools/ManifestMiner/out/manifest-draft.json, line ~707417) has Madden NFL 27 with steamAppId 3940610, banRisk null and safeRoute null, and there is no Madden override.

Two caveats that do not overturn the claim:
- The sequencing advice ("a compiled-in fail-closed floor", a new "SaveTransportRules" gate) is design reasoning built on these facts, not something the code can confirm.
- "Madden mined row is null" should say the banRisk field is null in the miner draft, and Madden is missing from the published feed entirely.

**What would settle what remains.** The claim holds as stated. One test would close the remaining gap: an xUnit test that registers a GameEntry with SteamAppId=null for a CFB27 install. Apply the cached remote feed and assert that BanRiskCatalog.ByAppId(entry.SteamAppId) == GameBanRisk.None and that MainViewModel's enable gate lets the enable through. That turns the reasoning into an observed failure before sub-project 1 changes anything.


### C5 — CONFIRMED

**Claim.** The Madden 27 side of cross-game transport is unverified. That Madden 27 saves use the same FBCHUNKS/zlib/FrTk layout as College Football is only INFERRED from the madden-franchise library's shared M26 strategy; no Madden 27 save exists yet (Documents\Madden NFL 27 absent, VERIFIED). EA's import only lands in Superstar, and Superstar reportedly needs to be online (INFERRED; help.ea.com timed out). Whether any offline Madden 27 mode (offline Franchise player career) can accept an externally written player row is UNKNOWN. EA's own import record (CollegeRtgImportInfo) carries no ratings (VERIFIED against schema 620), so the offline route cannot replay EA's import.

**Why it is load-bearing.** Sub-projects 3 and 4 both need a working offline Madden destination and a readable/writable Madden format. It sets the critical-path prerequisite (owner creates Superstar, offline Franchise and roster saves before design proceeds), the choice of target mode, and whether player-row insertion or only overwriting existing prospects/free agents is possible. It also frames the boundary review on not writing IsImported or other import flags.

**If wrong.** If Madden 27 saves use a different container or schema family, cross-game transport is two independent reverse-engineering projects rather than one translator. If no offline Madden mode can hold an externally written player (Superstar online-only, Franchise refusing inserted rows), the College-Football-to-Madden direction of sub-project 3 has no legitimate offline landing spot. The program shrinks to Madden-to-College-Football, or to overwriting existing Franchise players.

**Skeptic's reasoning.** The claim holds up. Each part I could check came back as stated, and the parts it calls INFERRED or UNKNOWN are honestly labelled. Three corrections sharpen it, and none reverses it.

(1) The claim understates the format evidence. It is not only that madden-franchise sends year 27 to M26Strategy. The library's README says "Madden 27 \| Full" support, next to "College Football 27 \| Full". The library also ships a Madden 27 schema (meta major 620, minor 0, gameYear 27). And one piece of code opens both games' files: a zlib inflate, then a check for the FrTk header. StrategyPicker sends College files to the Madden strategy for the same year, so both games take the same path. This is still a third-party claim, and no Madden 27 save exists on this machine to check it against. So "same container" stays INFERRED, but on firmer ground than the claim says.

(2) The claim that CollegeRtgImportInfo carries no ratings is slightly wrong. It has no attribute ratings, but it does carry one overall rating, CollegeOVR (int), plus CollegePosition, CollegePositionName, stats and awards arrays, and IsImported. Its conclusion still holds: one overall number cannot rebuild a player's full ratings, so the offline route cannot replay EA's import.

(3) One thing the claim does not mention: the M27 schema has DraftClassManager_IssueImportDraftClassRequest and DraftClassManager ImportDraftClassImportResponse. That looks like a Franchise draft-class import. It is a candidate offline landing spot, but whether it works fully offline is unknown.

Also, CollegeImportInfo sits on FranchiseUser, next to Superstar fields like SuperstarCachedThemeWeekGoals. That fits with EA's import landing in the Franchise player-career (Superstar) path, but it does not settle whether that path needs to be online.

**What would settle what remains.** Have the owner create Madden 27 saves: one offline Franchise player career, one Superstar, and one roster save. Copy them byte-for-byte to the scratchpad and check them for the FBCHUNKS container, zlib, the FrTk header and schema 620. Then test whether an offline Franchise save accepts a player row added at rest, and whether a draft-class import works with networking off.


## Detecting EA app installs

*15 verified, 3 inferred, 2 unknown.*

You can detect both games without the EA app, the network or any EA API. For each game there are three plain on-disk signals, all read-only. (1) The registry key HKLM\SOFTWARE\[WOW6432Node\]EA Sports\<Game Title> holds "Install Dir", "DisplayName", "Locale" and "Product GUID". (2) A Windows Uninstall key named by that Product GUID holds InstallLocation, DisplayIcon (the game exe), DisplayVersion and Publisher=Electronic Arts. (3) The file <Install Dir>\__Installer\installerdata.xml holds the EA contentID, gameTitle, gameVersion and launcher paths, and those launcher paths are written relative to the same EA Sports registry key. College Football 27 is fully installed and has all three: contentID 16425899, GUID {4BA2CEAA-...}, version 1.0.140.17622, exe CollegeFB27.exe. Madden NFL 27 is mid-install right now. It has no EA Sports registry key and no Uninstall key yet, and every file in its folder, installerdata.xml included, carries a "_DiP_Staged" suffix. Its staged manifest shows contentID 16425895, version 1.0.139.61898 and exe Madden27.exe. So "the registry key exists and __Installer\installerdata.xml exists without the _DiP_Staged suffix" is a working installed-vs-downloading check, much like Steam's StateFlags check. C:\ProgramData\EA Desktop\InstallData has one folder per title name with a base-<offerId> subfolder (base-Origin.SFT.50.0001619 for College Football, base-Origin.SFT.50.0001595 for Madden), but it holds no install path and outlives uninstalls: Battlefield 6 Event is listed there but is not in C:\Program Files\EA Games. Use it only as a hint. The encrypted IS file under the hashed ProgramData folder is not readable and you don't need it. In the launcher, the seam is IStoreLibrary (src/ModManager.App/Services/IStoreLibrary.cs) plus the store-neutral InstalledGame record (src/ModManager.Core/InstalledGame.cs). But only SteamService implements it, DI hands out a single implementation, and several consumers call SteamService directly or key everything on SteamAppId. The most serious case is BanRiskCatalog, which maps ban risk only from Stores.SteamAppId. A College Football 27 added from the EA app would carry no SteamAppId, so it would silently resolve to GameBanRisk.None and the required warn-and-acknowledge gate would never fire. For the EA identifier, I recommend adding StoreIds.EaContentId (for example "16425899"), which you can read offline from installerdata.xml. Keep the Origin.SFT.50.xxxxxxx offer id as optional extra data.

## Forensics on the College Football 27 save bytes

*20 verified, 5 inferred, 2 unknown.*

None of the College Football 27 saves are encrypted, and none carry an app-level checksum that I could find. Each save (PROFILE-COLLEGE, ROSTER-Official and all three RTG files) is a fixed-size 'FBCHUNKS' file: a small plaintext header, one zlib stream, then a fixed tail (zero padding, or leftover data in the RTG files). Python's zlib opens all of them cleanly, and zlib's built-in Adler-32 checks out, so every payload is plaintext after one inflate. The Road to Glory files unpack to a 31 MB 'FrTk' database with 2,455 schema tables (Player 17,500 records, CharacterVisuals 18,000, Coach, Team, Recruit, the stats tables). the character's first name sits in the Player table's string area. ROSTER-Official unpacks to a 14.2 MB tagged format using EA's classic 4-letter field codes (PFNA/PLNA/POVR/PSPD/PPOS/TGID...) for 11,730 players, plus 12,823 small gzip blobs holding each player's look. PROFILE-COLLEGE is the same tagged format and holds a save-slot index with a summary line per career ('<per-slot summary line: slot, id, school, opponent, character name, week, rating — redacted>'). Two tests found no integrity field. First, RTG-E and RTG-AUG30 differ in exactly 2 bytes, the header timestamp. Second, a table-by-table diff of RTG-E against RTG-E-AUTOSAVE shows the only header changes are counters (table count, a per-table save counter, next-record pointers), with nothing that behaves like a hash. The one encoded layer inside the payload is zstd frames in CharacterVisuals/CharacterGameplay, and they need a dictionary. Its ID (1711034507) matches the public data/zstd-dicts/c27/dict.bin in the open-source bep713/madden-franchise library. That library claims Full support for College Football 27 and Madden 19-27, runs College Football through the same code as Madden 26/27, and on save just re-deflates, patches a 3-byte length at 0x4A and keeps the rest of the file. So reading all files is possible now. Writing looks possible with no checksum to recompute beyond zlib's own, but no edited file has been loaded by the game, so that part is inferred, not proven. Two things are still unknown: whether the public College Football schema matches this game build (the header says schema 833; the library ships C27_468_2), and what one 4-byte field in the ROSTER header means.

## Community knowledge of the formats

*12 verified, 8 inferred, 0 unknown.*

You don't have to start from nothing: public source code already reads and writes these formats offline. The main library is bep713/madden-franchise (JS, MIT in package.json, updated 2026-08-04). It says it has full support for Madden 19-27 franchise saves and College Football 27 dynasty saves, and ships schemas M25_222, M26_682, M27_620 and C27_468. Its sister library bep713/madden-file-tools (MIT) reads and writes Madden roster files in the TDB2 format used since Madden 21. I checked its roster header layout against the copy of ROSTER-Official and it matches exactly: the year 2027 at 0x16, zlib data starting at 0x4A, the uncompressed length at 0x12, and a CRC at 0x1A. That CRC is CRC-32/BZIP2 (MSB-first, init and xorout FFFFFFFF) over the uncompressed data, the same algorithm the library writes. So the roster integrity check is a plain, known CRC, not a signature. Whether the game accepts a roster with a recomputed CRC has not been tested. The Road to Glory copies use the same layout as the franchise/dynasty saves that madden-franchise and two CFB27 projects (DaiyronW/tool, eric-levinson/cfb27-dynasty-modding) handle. That layout is an 0x52-byte FBCHUNKS header holding a 6-part timestamp, the name 'College-27-RL…' and the schema number. A zlib stream at 0x52 holds its compressed length at 0x4A and unpacks to a 'FrTk' table database. After it comes a mostly-zero tail that is not pure padding (it holds zstd-compressed CharacterVisuals data), inside a fixed 9,646,981-byte file. Public CFB27 notes report no checksum on dynasty saves. Two failures are documented: writing a save of the wrong total size, and letting the recompressed stream overrun the second chunk. The biggest risk is that the schema changes with patches: 468 in the library's test file, 809 in the July 2026 notes, and 833 in the owner's September Road to Glory copies. No public schema for 833 is known. Every Frostbite asset-modding route (FMT plugin, MMC startup proxy, Lua hook) depends on an anti-tamper proxy or DLL loaded when the game starts. The owner's boundary rules those out. Only at-rest save/roster editing fits. Superstar is the only mode EA's own import feeds. A Madden-side offline target is UNKNOWN until real Madden 27 saves exist.

**Risks raised**

- The schema drifts with every title update. A translator built against one build can silently corrupt saves after a patch. Detect the schema major and refuse unknown ones.
- Fixed save sizes: a re-packed save that grows past the zlib slot or changes total size hangs the game on load (documented failure). Needs a stronger compressor (libdeflate-class) and hard size gates.
- The CharacterVisuals chunk after the zlib slot uses a zstd dictionary that may not match the owner's build. Moving a character's appearance across games may be impossible even when ratings and identity move.
- Road to Glory and autosaves use a 5-chunk layout that differs from the reference dynasty save. The public writer is dynasty-only.
- Madden 27 Superstar reportedly needs to be online. If Madden 27 has no offline mode that holds a created player, the one-character Madden destination falls back to an offline Franchise player career or has no clean target.
- College Football-to-NFL league translation (conferences vs divisions, 85-man vs 53-man rosters, differing position enums and rating sets) has no public prior art at all.
- Community tools like FMT and the MMC hook ship anti-tamper bypass components. Users who already have them installed may be the source of the 'must move mods out and clear data paths' pain. The launcher must not interoperate with those components beyond detecting them and warning.

## How these games are modded today, and the stale-data pain

*18 verified, 2 inferred, 1 unknown.*

Both games are modded on PC today with Frostbite tool forks, not a folder drop. The main one is MMC Frosty Modding Tools (Madden Modding Community; closed binaries, latest V1.1.0.4, 2026-09-03). The other is the FMT (Frostbite Modding Tool) plugin FMT.Madden26Plugin, which covers Madden 26, Madden 27 and CFB27 and has public source. Mods are .fbmod files. The manager compiles them into a ModData copy of the game's Data folder (patched toc/sb/cas/cat plus layout.toc), then launches the game pointed at that folder (Frosty uses -dataPath or GAME_DATA_DIR). The part that matters most for this program: both current toolchains require replacing EA's anti-cheat launcher, EAAntiCheat.GameServiceLauncher.exe, with a community "fake" one. FMT also drops proxy DLLs (CryptBase.dll, dpapi.dll) into the game root. That is anti-cheat circumvention. The launcher cannot automate, recommend or bundle it without breaking the owner's boundary. The reported "move mods out and clear old data paths" pain maps most plausibly (INFERRED) onto four kinds of leftovers. (a) A stale ModData folder in the game root, built against an older title update. (b) Leftover CryptBase.dll/dpapi.dll plus a swapped or stale-backup anti-cheat exe. The MMC guide itself says a leftover CryptBase.dll triggers a crash-handler popup. (c) A Live Content Update cache at C:\ProgramData\Frostbite\<game>\LCU, which older Frosty refused to mod around and which the community deletes. On the owner's machine it was rewritten 10 minutes after the Sep 10 title update. (d) A machine-wide GAME_DATA_DIR variable that FrostyFix-style tools set, which breaks other Frostbite games. The FMT code gives a concrete reason it recurs after every update: it backs up the real anti-cheat exe only when no .backup already exists. After an EA update, the next compile overwrites the NEW real exe, and cleanup later restores the OLD backup. On the launcher side: its reversible disable (move to <library>\_626mods\<id>\direct-disabled or loose-disabled), LeftoverHoldings, the setup-needs-attention banner and the Steam build-change warning are all built around loose files and Steam. None of them sees Frostbite residue, EA-app builds, the LCU cache or ProgramData. Worse, DataDirForGame would put the holding folder at C:\Program Files\EA Games\_626mods, where BUILTIN\Users has only read/execute rights, and the launcher has no elevation. The honest fit is a read-only "Frostbite residue / is this install vanilla?" detector keyed to EA's installerdata.xml gameVersion, plus guidance toward the EA app's own Repair. Whether the launcher may also delete or restore third-party residue in an anti-cheat-owned folder is an owner decision.

## Translating players and rosters between the games

*20 verified, 2 inferred, 2 unknown.*

The strongest finding changes the whole plan. College Football 27 and Madden NFL 27 share one franchise-file engine and nearly one Player schema. I diffed the two games' franchise schemas from bep713/madden-franchise (C27_468_2 and M27_620_0). They share 255 Player fields, including every one of the ~55 *Rating fields, Position, PlayerType (archetype) and TraitDevelopment. All three enums are identical name-to-value. College has only 33 extra Player fields (SchoolYear, RedshirtStatus, ProspectStarRating, NIL, Physical/Mental ability slots, SkillGroupCaps). Madden has 134 extra (Contract, YearsPro, YearDrafted, PLYR_CAPSALARY, ContractStatus, College, and Original*Rating copies of every rating). So the translation is a mapping between two dialects of one data model, not between two unrelated formats. That makes a Core-side translator realistic. VERIFIED from schema data, and the owner's RTG-E copy decompresses to an FrTk franchise file. There is one dangerous trap. The TraitDevelopment enum gives College_Impact, College_Star and College_Elite the same integers (1, 2, 3) as Star, Superstar and XFactor. Copying the raw value turns every College Elite into a Madden X-Factor, so dev traits must be remapped by name, never copied. EA's own import lands in Madden as CollegeRtgImportInfo: CollegeOVR, CollegePosition, awards, stats, records, IsImported. It carries no ratings array. That implies EA rebuilds the pro player instead of copying ratings (INFERRED, and consistent with press saying you get 'a brand new OVR plus a ratings bonus'). Rating rescaling and league-level assignment (eligibility, 32 vs ~138 teams, draft vs free agent) are not answered by any source. Every number and policy below is my design, and should be calibrated from real data read at rest from both games rather than hardcoded. There is also a version gap. The owner's RTG saves carry schema major 833 in the header, but the public library bundles C27 schema 468. Field names probably survived; which fields and what they hold must be checked against the owner's installed build.

**Risks raised**

- Schema drift: the saves are at franchise schema 833, while the only public College 27 schema is 468. Title updates can re-type or re-order fields, and a wrong field map writes plausible-looking garbage.
- TraitDevelopment integer aliasing silently inflates or deflates dev tiers in both directions.
- OVR may be stored rather than recomputed. Players could show one OVR while playing like another, or the game could 'correct' imported values on load in ways we can't see.
- Madden's Original*Rating shadows and the progression and regression tables may pull translated ratings back toward generated baselines, or break career-phase logic.
- Integrity: hidden checksums, table cross-references (Player records referenced by Team, DepthChart, DraftPlayer, Contract rows) and array-capacity limits could make an inserted player crash the save or be dropped. Insertion is much riskier than overwriting an existing record.
- Appearance: CharacterVisuals is a shared field, but the asset and head libraries may differ between titles. A copied appearance could render wrong or crash.
- College roster size (about 85) is far above NFL's 53, and there are ~138 college teams to 32 NFL teams. League-level transport means generating or keeping many filler players, and team-balance logic can easily produce degenerate leagues (one superteam).
- Real-player likeness and names: moving licensed NFL players into college saves, or college NIL players into Madden, is fine for private offline use but must never be packaged or redistributed as a data set.
- Position conversion for Superstar (e.g. RTG OT into Madden) is a gameplay-changing choice that users may read as a bug.
- The 'honest but wrong' failure: a rescaling curve that looks reasonable but was never calibrated against real Madden rookie distributions yields confident, unfun results. All constants must come from measured data.

## The safe envelope

*13 verified, 3 inferred, 3 unknown.*

The owner's rule (edit saves only at rest, game closed, never touch Javelin or EA servers) is necessary. It is not enough on its own, and two facts found here change the plan. First, VERIFIED on the owner's own machine: the EA app cloud-syncs every College Football 27 save file except UserSettings.dat. Before each launch it takes a lock on EA's cloud copy and compares it with the local files. After each session it uploads the local files to EA's S3 storage. So an edited save does not stay offline. The next time the game is launched with the EA app online, the edit is either uploaded to EA or clobbered by the cloud copy, and which of those happens is UNKNOWN. Second, VERIFIED in the launcher's code: the ban-risk law would not fire for these games today. BanRiskCatalog looks up risk by Steam app id only. A game added by hand from the EA app has no Steam id, so it resolves to GameBanRisk.None. Nothing public says whether EA checks Road to Glory or roster data on its servers, or has banned anyone for offline save edits; both are UNKNOWN. Microsoft Store policy 7.19 has no clause about save editing or anti-cheat. The real Store exposure is keeping the reviewer-letter promise true ('does not bypass, disable or interfere with any anti-cheat system'), describing the feature accurately (10.1.1), and never shipping EA, NFL or college roster content (11.2). The workable envelope: gate every save write on a live risk lookup that fails closed; require the human's acknowledgement for each write, which an agent can never give; check that the game, Javelin and ideally the EA app are all closed; take a snapshot first; and tell the user plainly that the cloud sync will carry the edit to EA, or undo it, the next time they go online.

## Fitting the launcher's architecture

*20 verified, 3 inferred, 4 unknown.*

The launcher has most of the pieces this program needs: a pure Core with an App shell, a snapshot-first save editor with post-write checks (FromSoft), a multi-store `StoreIds` schema, profile-archive transport, and a Safe Clear / vanilla step-aside engine that already solves "move mods out" for other engines. But four things are keyed on Steam, and they will quietly break EA-app installs of both games unless they are fixed first. (1) VERIFIED: `BanRiskCatalog` maps ban risk only by `SteamAppId`, and every enable gate (MainViewModel, LibraryViewModel, the MCP `WriteTools`) asks it with `GameEntry.SteamAppId`. If an EA-app game is registered without a Steam id it resolves to `GameBanRisk.None`, so the high-risk gate and banner never appear. If it is registered with a Steam id (CFB27 is 4032350 in the shipped override; Madden 27 is 3940610 in the mined draft), `EnginePresets` sets `LaunchUrl=steam://rungameid/...`, which launches the wrong store. (2) VERIFIED: `SaveLocator`, `SaveDirHints`, `SaveLayoutCatalog`, `SaveSeamCatalog`, `LaunchOptions` and the SavesDialog character dispatch are all keyed on Steam app id. (3) VERIFIED: `SaveManager.ListSaveFiles` filters by file extension, and the CFB27 saves have none (RTG-E, ROSTER-Official, PROFILE-COLLEGE), so the saves panel would list nothing. (4) VERIFIED: the EA app leaves reliable, read-only detection signals: `HKLM\SOFTWARE\EA Sports\<title>\Install Dir` (note: not `EA Games`), `<install>\__Installer\installerdata.xml` (contentID, gameVersion, launcher exe), and `C:\ProgramData\EA Desktop\InstallData\<title>\base-Origin.SFT.50.0001619`. That means an `EaLibrary : IStoreLibrary` adapter can sit next to `SteamService`. From the bytes of the copies (VERIFIED): each save is an `FBCHUNKS` container with a version, a header length, a 2026-09-13 17:35:33-style timestamp that matches the file mtime, a game build tag (`College-27-RL4-9192662` vs `College-27-RL3_5-9171310`, which differ between RTG saves), zlib payloads, more than one compressed region in RTG files, and zero padding up to a fixed file size. So the Frostbite module needs a chunk-enumerating container reader and writer that respects capacity, plus a fail-closed allowlist of builds it is allowed to write. It should mirror `Bnd4Reader` + `EldenRingSave` (look sections up by structure, fail loud, snapshot first, atomic write, re-read to verify), and verification must compare decoded content rather than raw bytes. Proposed layout. Core: `Stores/Ea` (pure parsers), `SaveEditor/Frostbite` (container), `SaveEditor/Ea/CollegeFootball27` and `SaveEditor/Ea/Madden27` (schemas), `SaveTransport/Football` (a league-neutral model plus pure translators that return a loss report), and a `CrossGameTransferPlan` built on validate-then-write. App: `EaLibrary`, `FootballSaveService` (snapshot-first, both games closed), and a `SaveTransferDialog`. For sub-project 2, the community workflow in the sibling-fetched MMC guide requires replacing `EAAntiCheat.GameServiceLauncher.exe`. That is circumvention and outside the owner's boundary. So the launcher can offer reversible cleanup back to vanilla (becoming safer is never gated), but it cannot offer an enable-mods path for these games without crossing that line.

**Risks raised**

- Silent ban-risk bypass: an EA-app registration without a SteamAppId resolves to GameBanRisk.None today. A careless implementation of sub-project 1 would ship a high-risk game with no gate.
- Mis-launch: reusing the Steam quick-pick for these games sets LaunchUrl=steam://rungameid/4032350 on an EA-app install.
- Circumvention creep: the community enable path replaces EAAntiCheat.GameServiceLauncher.exe. Any LaunchOptions AntiCheatToggle entry, catalog tool entry or 'get it here' link for MMC would move the launcher over the owner's boundary. PathGate forbidden globs should list EAAntiCheat.* for these games, and a test should assert no AntiCheatToggle exists for their ids.
- Bricked saves: a writer that re-deflates past the fixed file size, drops the second compressed region, or writes for an unverified build tag could produce a save the game rejects. Snapshot-first plus post-write decode verification is the line back, but only for the target file.
- Multi-file roster transfers (roster plus franchise, or several targets) can partly fail. They need the RestorePointOrchestrator capture-all, seal, change-all order, not per-file best effort.
- Existing SaveManager.Restore and SaveBundle.Restore delete the whole saves folder before extracting (after an auto snapshot). Auto snapshots are pruned by Prune(keepLastAuto), so pre-transfer snapshots must be auto:false or the user's way back can be pruned.
- An edited roster or character imported into an online-connected mode (online Dynasty, Ultimate Team, online franchise) could be flagged by EA. Detecting which saves are online-connected is unknown, so the save-write warning must be explicit and the transfer should target offline save kinds only.
- Temp files (.tmp-<pid>) written inside the live saves folder could be picked up by EA app cloud sync if it syncs that folder (unknown).
- The build tag differs between saves on one machine (RL3_5 vs RL4). Yearly EA patches will move layouts, so a hardcoded offset schema will rot silently unless every read and write is gated on the build tag.
- Store SKU: shipping an EA save rewriter may draw certification scrutiny. Deciding late forces #if FULL surgery across Core and App.
- The MCP agent surface: a future agent tool for transport would inherit none of the save-write warning unless AgentWriteRules gains a refusal an agent cannot pass.
